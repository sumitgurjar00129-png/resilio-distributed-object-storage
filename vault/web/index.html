Quorum Overlap Theorem
R + W > N  (2 + 2 = 4 > 3)

By the Pigeonhole Principle, any subset of $R=2$ nodes chosen for reading and any subset of $W=2$ nodes chosen for writing from a cluster of $N=3$ must overlap in at least $(R + W - N) = (2 + 2 - 3) = 1$ storage node. Since that overlap node received the latest committed version and cryptographic SHA-256 ETag, stale reads are mathematically impossible.

Durability, Availability & Latency Trade-Off Matrix
Comparing quorum parameter configurations across distributed storage paradigms
Configuration Consistency Model Write Performance Read Performance Failure Tolerance Trade-Off Rationale
N=3, W=2, R=2 (Active Resilio) Strong (OCC) Fast (2/3 ACKs) Fast (2/3 ACKs) Tolerates 1 Node Failure Optimal balanced design. Guarantees fresh reads without single-point bottlenecks.
N=3, W=3, R=1 (Fast Reads) Strong Slow (All nodes must ACK) Ultra-Fast (1 ACK) 0 Write Failures (Writes blocked if 1 node dies) Optimizes read latency at the expense of write availability.
N=3, W=1, R=3 (Fast Writes) Strong Ultra-Fast (1 ACK) Slow (All nodes must ACK) 0 Read Failures (Reads blocked if 1 node dies) Optimizes ingest throughput at the expense of read availability.
N=3, W=1, R=1 (Eventual Consistency) Weak / Eventual Ultra-Fast Ultra-Fast Tolerates 2 Failures Allows stale reads and write conflicts. Requires complex CRDT or vector clocks.
Policy Settings Are Read-Only at Runtime
Quorum parameters ($N=3, W=2, R=2$) are declared in vault/config.py at cluster bootstrap. Dynamically altering quorum parameters without joint distributed consensus (e.g. Raft reconfiguration) creates a risk of split-brain anomalies during network partitions. Configuration changes must be performed through verified rolling deployment.
